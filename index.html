Project Introduction

Multi-Voltage Crypto Core Architecture

The crypto_top project is a high-performance ASIC cryptographic accelerator designed using 32nm CMOS technology. It contains around 30K standard cells and implements cryptographic operations such as AES-256 and SHA-3.

Cryptographic operations require high-speed computation, while control logic and peripheral interfaces operate at lower speeds. To reduce power consumption and meet SoC thermal constraints, the design uses a dual-voltage architecture based on voltage scaling.

Voltage Domains

The design is divided into two voltage domains:

  • High-Performance Domain (0.95V / VDD): Contains the main datapath and computational engines. Operates at 0.95V to achieve maximum performance and timing closure using saed32rvt_ss0p95v125c.db libraries.
  • Low-Power Domain (0.75V / VDDL): Includes control logic and low-speed peripherals. Operating at 0.75V significantly reduces dynamic power consumption using saed32rvt_ss0p75v125c.db libraries.

Physical Design Challenges

The multi-voltage architecture introduces several backend design complexities:

  • UPF-based power intent integration
  • Level shifters for signals crossing voltage domains
  • Dedicated voltage areas and power planning
  • MCMM timing analysis across multiple operating conditions

  • Converts logical area → physical region size
  • Calculates height (grid-aligned rounding)
  • Calculates width (derived from area/height ratio)
  • Ensures compatibility with placement site grid

3. Grid-Aware Physical Adjustment

  • Rounds dimensions to height grid: 1.672
  • Rounds dimensions to width grid: 0.152
  • Prevents placement and legalization violations

4. Region Definition & Guard Bands

  • Defines origin point (llx, lly)
  • Computes opposite corner (urx, ury)
  • Creates bounding box for voltage area
  • Applies guard band spacing (5.016 units) to isolate domain

Floorplan Iteration & Congestion Fix

This section shows a real physical design floorplan optimization cycle, where an initial high-utilization "Y-shaped" floorplan caused severe routing congestion, and then was corrected by resizing and rebalancing the core area.

Initial Floorplan Problem

The first floorplan used a Y-shaped boundary, which created uneven routing resources and congestion hotspots.

Problem Analysis

  • Core utilization: ~84.75% (too high for routing)
  • Severe routing congestion: ~70%
  • Total overflow: 377,057
  • High congestion GRCs: 69.13%
  • Horizontal routing overflow: 81.91% (critical bottleneck)
  • Vertical routing overflow: 56.36%

Root Cause Analysis

  • High utilization left insufficient routing whitespace
  • Irregular "Y-shape" created uneven routing channels
  • Horizontal congestion was especially severe
  • Placement had no room for detours or detangling nets

Fix Strategy

The floorplan was re-initialized with improved geometry and reduced density.

Key Changes

  • Expanded and reshaped boundary for better routing flow
  • Reduced core utilization from ~84.75% to ~76.71%
  • Improved routing channel distribution
  • Preserved Y-shape structure but made it more routing-friendly

Final Outcome

  • Core utilization reduced to 76.71% (safe range)
  • Improved routing feasibility
  • Significantly lower congestion risk

Engineering Insight

High utilization + irregular floorplan shapes = routing congestion explosion

Even if placement fits, routing will fail without proper whitespace planning.

Floorplan Initialization – A Shape

This step initializes the chip floorplan for the multi-voltage cryptographic SoC by defining the core area, boundary shape, site rows, and routing tracks. It forms the foundation for all later physical design stages like placement, power planning, CTS, and routing.

Core Concept

The command defines a custom, non-rectangular floorplan boundary, which allows flexible chip shaping instead of a simple rectangular die. This is useful for realistic ASIC designs where IOs, macros, or power regions may require irregular boundaries.

What This Flow Does

1. Clears Existing Floorplan

  • Removes any previously created floorplan objects
  • Ensures a clean restart of physical design setup

2. Defines Chip Boundary

The boundary is defined as a polygon with coordinates that create a custom stepped floorplan shape, instead of a simple rectangle.

3. Core Creation

  • Core region is generated inside the boundary
  • Core utilization = ~80.32%
  • Ensures balance between area efficiency and routing congestion margin

4. Site Array Generation

  • Standard-cell rows (site rows) are created
  • Cells will be placed aligned to these rows
  • Floorplan snaps to manufacturing-compatible grid

5. Routing Track Setup

  • Routing tracks are automatically generated
  • Enables uniform routing resources across the chip
  • Prepares design for congestion-aware placement and routing

6. Core Alignment Fix

  • Core boundary snaps to site grid
  • Ensures legality for standard cell placement
  • Prevents placement misalignment issues later

Why This Step Matters

This is the base physical structure of the chip, and it directly impacts:

  • Placement quality
  • Congestion behavior
  • Timing closure
  • Power grid quality
  • Routing efficiency

A poorly defined floorplan here can break the entire backend flow.

MCMM Constraints - Multi-Corner Multi-Mode

MCMM (Multi-Corner Multi-Mode) timing analysis is critical for ensuring robust physical design closure across multiple operating conditions. This section provides comprehensive details on the MCMM setup and constraint methodology used in the crypto_top project.

MCMM Overview

Multi-Corner Multi-Mode analysis ensures that the design meets timing requirements across:

  • Process Corners: FF (Fast-Fast) and SS (Slow-Slow)
  • Temperature Conditions: -40°C and 125°C
  • Operating Modes: Functional and Scan/Test
  • Voltage Domains: 0.95V and 0.75V

Corner Specifications

Corner Process Temperature Library Use Case
FF (-40°C) Fast-Fast -40°C saed32rvt_ss0p95v_m40c.db Best-case hold analysis
SS (125°C) Slow-Slow 125°C saed32rvt_ss0p95v125c.db Worst-case setup analysis

Operating Modes

Functional Mode

  • Normal operational mode
  • Encryption/decryption operations
  • Core cryptographic functions active

Scan/Test Mode

  • Test/Debug operational mode
  • Scan chain enabled
  • Different timing characteristics due to scan path

MCMM Analysis Benefits

  • Comprehensive timing coverage across all operating conditions
  • Detects timing failures that single-corner analysis might miss
  • Ensures hold time compliance in best-case conditions
  • Ensures setup time compliance in worst-case conditions
  • Enables efficient multi-voltage timing closure
  • Reduces silicon failure risk and improves reliability

Constraint Management in Physical Design

During physical design stages (placement, CTS, routing), MCMM constraints guide:

  • Placement Optimization: Cell placement to minimize critical path delays
  • Clock Tree Synthesis: Clock skew control across all corners
  • Routing: Wire routing prioritizing critical timing paths
  • Signoff Analysis: Final timing verification across all scenarios
